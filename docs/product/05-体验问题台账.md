# 体验问题台账

维护日期：2026-10-28。原则：发现即记录，区分证据与推测，修复后复测。不会因记录而自动安排定时任务、指派他人或发送通知。

## 分级与处理

- P0：越权、数据泄露或大范围错误统计。停止相关路径，优先修复，不等集中排期。
- P1：任务无法完成、静默改变口径、关键结果可能被误解。尽快复现并处理；若先缓解，保留根因问题。
- P2：任务能完成，但效率、理解或便利性明显受影响。集中评审，按任务阶段安排成批修改。
- P3：轻微文案与视觉一致性。集中处理；如果影响可访问性或操作，应重新定级。

状态：待复现 → 已确认 → 待排期 → 修复中 → 待复测 → 已关闭。另可标“部分缓解”“待验证假设”“不处理（附理由）”。不能以“已写代码”直接关闭问题。

## 新问题记录模板

编号；发现日期；发现人/来源；角色与任务；页面及数据环境；前提与复现步骤；预期结果；实际结果；截图或日志证据；影响范围与严重程度；出现频率（未知则写未知）；临时处理；可能原因（标假设）；关联需求；实现责任角色（未分配则明确）；状态；修复版本；复测方法、结果、日期与证据；未解决边界。

## 集中修改流程

1. 试用过程中记录问题，不为每个轻微问题立刻打断主任务；数值或权限错误立即停止相关路径核查。
2. 合并重复问题，以任务受影响的结果描述问题，避免直接把某个按钮设计当成需求。
3. 每批开发前评审证据与影响，选择要解决的问题，写清验收标准和范围。
4. 修复后先做正确性回归，再按原复现路径和异常分支复测；没有复测的状态保持“待复测”。
5. 更新台账、用户故事地图和需求状态；真实用户观察结果单独更新价值验证，不能被自动测试替代。
