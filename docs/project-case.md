# 项目案例：把问数结果接到经营交付

## 起点与贡献范围

项目以用户提供的 AskData Studio v2.1.1 为底座。原代码包已包含 Vue 问数界面、FastAPI/LangGraph 路由、Schema 检索、MCP 工具、短视频合成数据及评测脚本。本项目没有将这些已有能力表述为从零开发。

本轮由项目作者主导问题定义、场景取舍与试用反馈，使用 AI 辅助开发和验证，主要迭代内容为：

- 接入 Olist 真实匿名历史样本，保留原字段、日期、币种与缺失值；建立中文目录、指标与跨明细连接约束。
- 将界面从对话展示扩展为经营任务工作台：范围确认、标准复盘、下钻、报告交付、分析复用。
- 用固定结果快照承接分页、筛选、统计和导出，避免只看到截断的前几行。
- 增加会话与来源隔离、重启恢复、CSV 管理、报告人工补充与草稿恢复。
- 用实际请求事件展示模型、工具、重试、耗时和 Token，区分传输成功与业务生成失败。
- 建立用户故事地图、旅程、需求与验证、体验台账；将复杂业务试用发现的反例纳入迭代。

尚无组织内真实业务部署、外部用户访谈或商业效果数据。文中的“运营负责人”等角色均为模拟情境。

## 三个重要取舍

### 固定口径和自由问数分别承担不同任务

月度复盘有明确口径，可用后端标准 SQL 稳定计算；自由问数适合探索，但需要先确认问题、检索字段和验证范围。因此两者共存。标准路径显示 0 次模型调用是正常行为，页面解释执行方式，避免让“调用多”成为价值指标。

### 失败时保留事实，但不宣称已交付

自动报告可能把其他月份或范围的数字写入正文。产品校验引用数值与范围，失败时保留事实和来源，允许人工补充。v12 的两次自动报告均触发回退，指定的一页图文材料没有完成；这被记为业务缺陷，而不是包装为成功。

### 复杂条件不能默默丢掉

“继续看这些订单”“排除某品类”“上个月”等话语容易让范围漂移。对已验证单值范围提供确认续查；未知组合和复杂群体继续提示补全，而不是以一个看似合理的查询替代原问题。现有保护是有限支持，并非通用语义正确性的证明。

## 迭代方式

收到业务目标后，先走完整任务，再记录卡点。每个问题关联角色、场景、具体动作、预期和实际、影响、优先级、验收、状态和证据。

正确性和权限问题优先解决；小的体验问题可以集中评审。测试通过后，还要实际重跑对应业务问题，并用独立 SQL 或 CSV 核对。原始发现和修复后的支持范围分别保留，不因把需求写进地图就标记已完成。

## 目前学到什么

可观察性必须覆盖业务结果：45 次模型 HTTP 请求都成功，依然可能有报告未完成。任务进度也需要描述“待核查什么”，而非只展示后台阶段。对账结果与来源、人工修改和恢复能力，都属于业务工作流本身。

v16 已按原例修复复杂报告与来源数量问题，并完成线上六来源图文报告验收，见 [v16 记录](evidence/v16-experience-fixes.md)。接下来继续观察真实业务人员如何完成复盘，确认哪些操作减少重做、哪些仍需其他工具。
